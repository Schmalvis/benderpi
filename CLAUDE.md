# BenderPi — Claude Code Context

Full context for AI-assisted development on the BenderPi voice assistant project.

---

## What This Is

A Raspberry Pi 5 voice assistant with the personality of Bender Bending Rodriguez (Futurama). Responds to the wake word **"Hey Bender"**, engages in multi-turn conversation, controls Home Assistant devices, gives weather/news briefings, and falls back to the Claude API for unknown queries. Voice is generated by a fine-tuned Piper TTS model trained on Bender audio clips.

**GitHub:** `git@github.com:Schmalvis/benderpi.git`

---

## Design Philosophy

**Offline-first.** BenderPi is designed to run entirely locally — internet access is not required for core functionality. The Hailo AI HAT+ (Hailo-10H, 40 TOPS NPU) provides dedicated hardware acceleration for STT (Whisper) and LLM (Qwen2.5-1.5B) inference on-device. Cloud APIs are a last resort, used only when local quality checks fail.

**AI response priority order:**
1. Static WAV clips — instant, zero compute
2. Pre-generated TTS — instant playback
3. Hailo NPU LLM — Qwen2.5-1.5B-Instruct via HailoRT GenAI (on-chip, ~3-8s)
4. Ollama CPU fallback — only if Hailo unavailable
5. Claude API (cloud) — only if local quality check fails (hedge phrases, too short)

**Routing config (`bender_config.json`):**
- `ai_backend: "hybrid"` + `ai_routing.*: "local_first"` — NPU first, cloud fallback on quality fail
- `ai_backend: "local_only"` — never touch cloud
- `ai_backend: "cloud_only"` — always use Claude API (avoid unless debugging)

## Hardware

| Component | Detail |
|---|---|
| Board | Raspberry Pi 5 |
| AI Accelerator | Hailo AI HAT+ (Hailo-10H, 40 TOPS NPU) — LLM + STT + vision inference |
| Camera | Raspberry Pi Camera Module 3 (IMX708, autofocus via dw9807) — used for VLM / scene analysis. **Not** the AI Camera: there is no on-sensor accelerator, so all vision inference runs on the Hailo NPU or the CPU |
| Audio HAT | ReSpeaker 2-Mic Pi HAT (WM8960 codec) — I2S, 2x MEMS mics |
| Speaker | 3W passive, connected to ReSpeaker HAT |
| LEDs | 45x WS2812B addressable RGB |
| LED Data | GPIO 10 / SPI MOSI — SPI enabled in `/boot/firmware/config.txt` |
| Presence sensor | VL53L0X time-of-flight, I2C bus 1 at `0x29` (GPIO 2 SDA / GPIO 3 SCL), **XSHUT on GPIO 17 / pin 11**. **Optional** — gates the Halloween open mic. Bus 1 otherwise holds only `0x1a`, the WM8960 codec, so there is no address clash. Needs `adafruit-circuitpython-vl53l0x` |
| ALSA card | Card 2 (`seeed-2mic-voicecard`, `hw:2,0`) |

### Critical audio constraint
The WM8960 can only operate at **one sample rate** at a time. The mic (openWakeWord wake word) runs at 16000Hz; playback runs at 44100Hz. **You cannot have both the input and output streams open simultaneously** — the output stream must be closed while listening for the wake word.

This is why `audio.py` uses `open_session()` / `close_session()` rather than a persistent stream.

| `stt_min_speech_ms` | `250` | Minimum **voiced** audio (VAD-positive frames) for a capture to be transcribed at all. Applies to *both* backends because it gates on the audio, before transcription. Added 2026-08-01 after a live session answered two captures of room noise (`"So, So"`, `"I'm going to do the"`) as if they were questions. Deliberately permissive — `"stop"`/`"bye"` must survive, and a Bender that ignores you is worse than one that occasionally answers a door slam. A capture whose VAD never fired at all (`term_reason == "no_speech"`) is now discarded unconditionally: it previously *was* transcribed, because a silence-only capture runs the full `max_record_seconds` and so cleared the minimum-length check — asking Whisper to transcribe pure silence is the classic hallucination generator |
| `stt_onset_frames` | `3` | Consecutive VAD-positive 30ms frames before a capture starts (90ms of continuous voice). Was effectively `1`: a door slam or a consonant from across the room started a capture, 750ms of silence ended it, the 250ms gate rejected it, and the loop re-entered — reopening the mic stream and discarding the first 210ms of whatever the user had begun saying. Live 2026-08-04: eight rejected 120ms captures in nine seconds. Set to `1` to restore the old behaviour |
| `stt_vad_warmup_frames` | `5` | Frames fed to the freshly built webrtcvad instance and ignored for onset. A fresh instance reports its first 3–5 frames as speech on quiet-room audio (reproduced offline 2026-09-08 on a device recording, all three aggressiveness modes), and every capture builds a fresh instance — so every capture opened with a fake 120–150ms utterance, the 250ms gate rejected it, and the loop re-entered: one rejected capture every 0.97s, ten in a row live. Level-independent, so quiet speech ("Okay." measured at RMS 81) is untouched; that is why `stt_min_speech_rms` stays off. `0` disables |
| `stt_speech_onset_timeout_s` | `6.0` | Seconds a capture waits for speech onset before returning `no_speech` (`0` = wait the full `max_record_seconds`). A silent window used to run the full 15s, so the idle tail of a session was 15–30s and 15s of background chatter reached Whisper. **Idle behaviour now:** the idle clock starts when Bender *finishes replying* (previously when the user finished speaking, so a long answer ate the whole `silence_timeout`), an empty window returns after ~6s, and the session ends on the first empty window that starts more than `silence_timeout` (8s) after the last reply — in practice the second empty window, ~12s |
| `stt_min_speech_rms` | `0` (off) | Voiced-audio level floor. Background chatter and a TV carry across a room at a much lower level than someone addressing the device, but the right floor is room-specific, so this ships disabled. Set it from the `stt_capture` metric (below) rather than by guesswork |
| `hailo_stt_enabled` | `true` | Route STT through the Hailo NPU (Whisper) rather than CPU faster-whisper |
| `vlm_enabled` | `false` | Gate for Qwen2-VL scene description (`vlm.py`) — off by default because the VLM cannot be resident alongside the LLM (KV-Cache singleton, see below). **Three readers now, one until 2026-10-15.** `wake_converse.py` was the only one, so `POST /api/vision/analyse` and `VisionHandler` both tried the VLM however the flag was set, and both reported the failure as a fact about the room — see the vision honesty note under Known Issues. The route now returns 503, `GET /api/puppet/camera/status` reports it as `vision_enabled` so the Puppet page hides the Ask Bender button, and `VisionHandler` says the eyes do not work |
| `presence_sensor_enabled` | `false` | Gate the **Halloween open mic** behind a VL53L0X time-of-flight sensor (`scripts/presence.py`). Halloween mode drops the wake word, so any nearby speech starts a session — **measured 2026-10-10** by replaying 5.25h of recorded speech near the array through the real capture gates: **465 sessions, 88.6/hour, Bender in a session 79% of the time**. The cost is not noise, it is **deafness**: a false session runs a greeting, one reply and two empty 6s captures before timing out, so the child who actually arrived is ignored for 22–45s. `stt_min_speech_rms` **cannot** gate this, although the Halloween plan assumed it could — the same measurement found `voiced_rms` does not track distance on the XVF3800 (`close_normal` has the **lowest** median of any condition at 342; `seated_far` reads 1432), so a level floor rejects the child at the door before the voice across the room: at 1200 it cuts 57% of far-field and 56% of near-field. The camera cannot gate it either — the board is a **Camera Module 3 (IMX708)** with no on-sensor accelerator, and a doorstep on 31 October is dark. **Fails open by design**: a missing, unwired or broken sensor leaves `_halloween_loop` exactly as it was, because the owner's worst acceptable failure is a silent Bender, not a chatty one. Verify the hardware first with `venv/bin/python scripts/probe_vl53l0x.py --xshut 17`. **The gate itself was verified against the real sensor 2026-10-13**, by enabling it in process and calling `present()` in a loop at the shipped thresholds: 3 arrivals (at 767, 888 and 848 mm), 3 departures, 435 reads, **0 errors**, closest approach 322 mm, and no spurious transitions. That run also found the gate's own crash: `presence.py` did `import metrics`, binding the module rather than the `MetricsWriter` singleton, so all 15 `metrics.count(...)` calls raised `AttributeError` out of `available()` and would have taken `_halloween_loop` down on the first open. **The fail-open rule does not cover that**: it covers exceptions from the sensor, caught inside `distance_mm()`. The test fixture monkeypatched `presence.metrics`, so no test could see it |
| `presence_max_mm` | `2000` (code default), **`1000` shipped in `bender_config.json`** | Gate distance in millimetres. The 2 m code default is the stated doorstep requirement and also the VL53L0X's specified limit **in good conditions**, and this build does not reach it. **MEASURED on-device 2026-10-13**, sensor mounted behind the left eye, walking in from 3 m and back out, 0 errors in every run: at the driver's default 0.25 MCPS signal rate limit the gate was reliable to **641 mm** and never saw past **872 mm**; at 0.0938 MCPS it tracked **18 consecutive reads from 407 mm to 1267 mm** with no dropout. Three independent numbers put the noise ceiling at about 1200 mm: an empty-field stray at **1220 mm**, a walk maximum of **1233 mm** at a 500 ms budget, and **1267 mm** at 200 ms. So `1000` sits below the ceiling and inside the proven tracked zone. The owner's own requirement made 2 m moot: children come to **arm's reach, 400-600 mm**, to take candy from the chest cavity, so 1000 mm leaves 400 mm of margin. Set it from the probe output, not from the datasheet |
| `presence_min_mm` | `0` (off), **`0` confirmed on this build** | **Crosstalk floor.** The VL53L0X times its own IR pulse back, so it cannot tell Bender's eye socket from a child: any enclosure surface inside the ~25° cone returns a short, *stable* reading with nobody there. That failure **latches the gate open forever while looking exactly like a working sensor** — worse than the sensor dying, because dying fails open and says so. Readings at or under this are discarded and counted (`presence_below_floor`). Ships at 0 because the right value depends on the mounting: set it from `scripts/probe_vl53l0x.py --xshut 17 --baseline`. **Mount flush with an open aperture and no window** — a cover needs crosstalk calibration the Adafruit driver does not expose. On this build the left eye's blank pupil square mirrors the camera in the right eye and puts the sensor flush; recessing it in the head cavity does not **PASSED on this build 2026-10-13**, twice: an empty field read **0 of 91 in range** at 0.25 MCPS and **0 of 135** at 0.0938 MCPS, so the mounting has no crosstalk and the floor stays off. ### Hailo residency (`scripts/hailo_hub.py`)

**The resource model, established by on-device spike 2026-07-30:**

```
Whisper + (LLM XOR VLM), all resident, for the life of the process
```

Whisper and Qwen **can** be loaded at the same time — verified on-device
(Whisper-Small + Qwen2.5-1.5B on one shared VDevice, interleaved STT→LLM→STT
inference, STT latency with the LLM resident identical to STT alone). This
matches Hailo's own reference app (`hailo_apps/python/gen_ai_apps/voice_assistant/`),
which builds one `VDevice` in the `SHARED` group, constructs both `Speech2Text`
and `LLM` on it, and holds both for the process lifetime.

The real constraint is narrower than "one model at a time": the on-chip
**KV-Cache is a singleton**. Whisper doesn't use it; the LLM and the VLM each
need exclusive hold, so loading the VLM alongside the LLM fails with
`HAILO_INVALID_OPERATION(6): KV-Cache is already in use`. That is the mechanical
reason `vlm_enabled` is off — not superstition, and not fixable by ordering.

`hailo_hub` owns the VDevice and both model handles. `stt.py` and `ai_local.py`
borrow handles from it and never release them; `hailo_hub.close()` (registered
via `atexit`, idempotent) tears down at process exit, models before the VDevice.
Both models are pre-loaded on the startup warm-up thread, so neither the first
wake word nor the first AI turn pays an init delay.

**Proof it is working:** `ai_hailo_load` should appear **once per process**
instead of once per AI turn, and `ai_hailo_stt_load` once per process. Both show
up in STATUS.md with no new instrumentation. Measured on-device: STT load ~3.0s,
LLM load ~9.7s — paid once at startup instead of per turn.

**Rollback:** set `hailo_resident: false`. The legacy per-turn release/reload
path (`stt.release()`, `release_chip()`, `reset_hailo()`) is still present and
still tested; those three calls simply become no-ops when residency is on. The
one property residency has *not* proven is multi-week stability of a
permanently-held VDevice, which is why the flag exists.

### On-chip conversation context — read this before touching `ai_local.py`

HailoRT keeps conversation context **on the chip** between `generate()` calls,
and **rejects a system-role message on any call after the first**:

```
[HailoRT] [error] CHECK failed - System role messages can only be provided on the first prompt
                                        -> HAILO_INVALID_OPERATION(6)
```

So the protocol is: **system prompt exactly once per context, then only the new
user message.** Do not resend history — the chip already has it. Sending
`[system, *history]` every turn (the pre-residency shape) raises on turn 2.

This was invisible before residency because the LLM object was destroyed and
rebuilt every turn, making every turn a fresh context. Holding it resident
exposed the rule, and briefly shipped a bug where turn 2+ of a session failed
over to Ollama (fixed same day).

Not resending history is also *faster*, not just required: measured TTFT drops
from **~1101ms on a fresh context to ~371ms** on later turns, because the model
stops re-encoding the whole conversation each time.

`_HailoLLMResponder` tracks `_context_fresh` / `_context_turns` instead of a
message list. `clear_context()` is the only way back to a fresh context, and is
called on: session end (`clear_history()`), a quality-gate rejection (so a
rejected reply doesn't become context for the cloud-escalated turn), and every
`ai_max_history` turns (on-chip context can only be cleared wholesale, so it is
recycled rather than trimmed).

### Hailo token streaming

`LLM.generate()` **is** a token-streaming context manager on HailoRT 5.3 — an
older comment in `ai_local.py` claiming otherwise was wrong. The Hailo path
streams sentence-by-sentence into the same `ResponseStream` pipeline the Ollama
and cloud paths use, so Piper starts speaking sentence 1 while the model is
still decoding sentence 2.

- `<|im_end|>` arrives as its own discrete token (verified on-device); it is
  filtered per-token and stripped from the buffer, and a trailing partial
  `<|…` fragment is dropped so it can never be spoken aloud.
- Only the **first sentence** is quality-checked — hedges and character breaks
  appear at the start, and once audio is playing it cannot be taken back.
- Aborting mid-stream is safe (verified on-device): the `with` block closes the
  completion and the next `generate()` works normally.
- **Ollama failover applies only before the first sentence is yielded.** Once
  audio is playing, a mid-stream Hailo failure ends the turn early rather than
  splicing a second model's voice onto the first.

Measured end-to-end on-device across a 5-turn session: first sentence in
**665–3580ms (mean ~2.1s)**, versus a 14,563ms `ai_local_first_sentence_ms`
median before. New metric: `ai_hailo_ttfs` (time to first spoken sentence).

`watchdog_config.json` keys:
- `max_hours_without_session` (code default `6`, shipped `72` in `watchdog_config.json`) — alerts if no conversation session detected in N hours. Raised to 72h because real usage is sparse (days between sessions), so 6h flagged normal idle as an anomaly. NB: `check_session_liveness` matches session_start events by `"type"` (the real `conversation_log.py` schema) — a prior `"event"`-key typo made it always report "no sessions found" regardless of activity. **It says nothing where `service_liveness_unit` is not installed on this box** (2026-10-14): a dev clone never runs the conversation service, so "No session_start events found in /home/pi/projects/benderpi/logs" was pure noise there, and it arrived next to two mic-stall alerts the test suite had manufactured in the dev clone's own `logs/metrics.jsonl` while the real device had 0 stalls and 0 restarts. Only an **explicit** "not installed" silences it — `_unit_is_installed()` returns `True`/`False`/`None`, and `None` ("systemctl missing or the call failed") still alerts, so a device whose systemctl broke is not quietly exempted. That is why it is a separate probe from `_probe_unit_state`, whose `None` conflates the two.
- `mic_stall_reinit_threshold` (default `3`) — warns if the wake loop reinitialised the mic after a stall this many times in `mic_stall_lookback_hours` (USB mic flapping).
- `mic_stall_exit_threshold` (default `1`) — errors if the service exited for a systemd restart after an unrecoverable mic stall (mic likely needs a physical reseat), counted over `mic_stall_lookback_hours`.
- `service_liveness_enabled` / `service_liveness_unit` (default `true` / `bender-converse`) — alerts (severity `error`) if the conversation service is not running. **The only check not derived from metrics**, and the only one that can see its own absence: a dead process emits no metrics, so every other check goes quiet exactly when things are worst, and `max_hours_without_session` tolerates 72h of silence by design. Added after a 2026-07-30 outage where a failed deploy plus a *failed rollback restart* (systemd `StartLimitBurst` exhausted) left the service in `failed` with nothing to report it. Probes `systemctl show -p LoadState -p ActiveState`: `LoadState != loaded` (unit not installed on this box, e.g. a dev clone) returns "no opinion" rather than an alert, and `activating`/`reloading` are healthy so a deploy restart mid-tick isn't flagged.
- `mic_stall_lookback_hours` (default `24`) — window the two mic-stall checks above count events over. Deliberately shorter than the general `lookback_hours` (168h/7d): these checks answer "is the mic actively flapping right now", and a resolved burst counted over a full week kept re-triggering the same HA card on every 15-min watchdog tick for days after the underlying bug (a false-positive RMS-floor dead-mic sentinel, fixed in `eae30fa`) was already fixed and deployed (2026-07-18 incident).
- `log_retention_days` (default `90`) — conversation logs (`logs/YYYY-MM-DD.jsonl`) older than this are deleted by `watchdog_notify.py`'s retention sweep. Never touches `metrics.jsonl` (that's size-rotated, see below).
- `watchdog_renotify_hours` (default `12`) — a still-firing alert only re-pushes to HA after this many hours, so a persistent condition pings once instead of every timer tick.
- `watchdog_quiet_hours_start` / `watchdog_quiet_hours_end` (default `23` / `7`, local time, wraps midnight) — suppresses HA pushes during this window (cooldown bookkeeping still happens). **Only applies to the `notify.*` push path** — the default `persistent_notification` path is a silent, self-managing card (see below), so quiet hours don't gate it.
- `watchdog_notify_domain` / `watchdog_notify_service` (default `persistent_notification` / `create`, always exists on any HA instance) — the `POST /api/services/<domain>/<service>` target for alert pushes. Override with a real `notify.*` service (e.g. `notify` / `mobile_app_yourphone`) for a phone push instead of an HA persistent-notification card. The two domains take different code paths (see below): `persistent_notification` → one self-updating/auto-dismissing card; `notify.*` → cooldown + quiet-hours-gated pushes.

**systemd:** Service uses `Type=notify` + `WatchdogSec=120`, plus `TimeoutStopSec=20` / `TimeoutAbortSec=20` so a wedged process gets SIGKILLed instead of sticking in "deactivating". `StartLimitIntervalSec=300` / `StartLimitBurst=5` caps crash-restart thrash — after 5 start attempts (automatic *or* manual, e.g. a `git_pull.sh` restart) in 300s the unit lands in "failed" and stops retrying; recover with `sudo systemctl reset-failed bender-converse && sudo systemctl start bender-converse`.

> ⚠️ **Do not run the test suite on the device while `bender-converse` is running.** The full suite takes ~68s of near-saturating CPU on a 4GB Pi 5, which starves `audio.MicReader`'s reader thread past `mic_read_timeout_s` (10s). The wake loop then raises `MicStallError`, reinits once, and `sys.exit(1)`s for systemd to restart it — a healthy mic misdiagnosed as a wedged one. On 2026-07-30 four `wake_loop_stall_exit` events (22:20, 22:59, 23:00, 23:06) each correlated exactly with a device-side `pytest` run, and those four systemd restarts are what actually exhausted the start limit below. Run the suite on a dev clone, or `systemctl stop bender-converse` first.

> ⚠️ **An ordinary working session exhausts this budget.** Two or three deploys plus a couple of `systemctl stop`/`start` cycles for an on-device spike is already 5 starts in 300s. When that happens the *next* deploy fails its restart gate, `git_pull.sh` rolls back — **and its rollback restart hits the same limit**, so the service is left down and the commit is falsely marked bad in `.git_pull_bad_sha`. This happened on 2026-07-30 (~4 min outage). If a restart fails, check `systemctl show bender-converse -p Result` for `start-limit-hit` **before** suspecting your code, then `reset-failed` + `start`, and delete `.git_pull_bad_sha` if the rolled-back commit was innocent. Space restarts out, or `reset-failed` between them. The `service_liveness` watchdog check (below) exists specifically so this state gets reported rather than sitting silent for up to 72h. Requires `libsystemd-dev pkg-config` (apt) and `systemd-python` (pip). After updating the service file: `sudo cp systemd/bender-converse.service /etc/systemd/system/ && sudo systemctl daemon-reload`. **Important:** auto-deploy (`scripts/git_pull.sh`) only pulls source files — it never installs unit files. Any change to `systemd/*.service` must be manually copied + `daemon-reload`ed on the Pi to take effect, even after the git pull lands.

**Mic stall watchdog (MicReader):** All blocking mic reads (wake-word loop + STT recording) go through `audio.MicReader`, a daemon reader thread + queue with a `mic_read_timeout_s` timeout. A wedged USB read raises `MicStallError` (subclass of `RuntimeError`) on the consumer thread so the process can log, feed the systemd watchdog, and escalate instead of hanging forever. Escalation policy: reinit the mic up to `mic_stall_max_reinits` times, then `sys.exit(1)` and let systemd's `Restart=on-failure` recover. A startup `audio.mic_selftest()` reads ~1s of frames and WARNs (non-blocking) if the mic path looks wedged or silent.

**Watchdog alert push (`bender-watchdog.timer`):** `scripts/watchdog.py` is a library, not a daemon — nothing ran `run_checks()` between deploys until now. `scripts/watchdog_notify.py` runs the checks, sweeps `logs/*.jsonl` older than `log_retention_days`, and syncs the non-empty alert list to Home Assistant (reusing `HA_URL`/`HA_TOKEN`), tracking state in `logs/.watchdog_state.json` (gitignored). Install manually (git pull does not install units): `sudo cp systemd/bender-watchdog.service systemd/bender-watchdog.timer /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl enable --now bender-watchdog.timer`. Runs every 15 minutes (`OnUnitActiveSec=15min`). Manual run: `venv/bin/python scripts/watchdog_notify.py`.

`main()` branches on `watchdog_notify_domain` (`_run_persistent_card` vs `_run_push_notify`):
- **`persistent_notification` (default):** keeps ONE managed card (fixed `notification_id` `bender_watchdog`) in sync with the current alert set — re-`create`d in place each run (no pile-up), and **dismissed automatically** via `persistent_notification/dismiss` the moment all checks go green (`card_active` flag in the state file). Cards are silent (no phone push), so this path skips the renotify cooldown and quiet hours. Only shows in HA's notification UI, not as a phone push. NB: HA removed `persistent_notification.*` from the state machine, so these cards do **not** appear in `GET /api/states` — the `create`/`dismiss` service calls still return 200.
- **`notify.*` (phone push):** a push can't be recalled, so this path keeps the per-check renotify cooldown (`watchdog_renotify_hours`) and quiet-hours suppression, batching due alerts into one push. Set `watchdog_notify_domain`/`_service` to a real `notify.*` service (e.g. your HA mobile app's) to use it.

**`metrics.jsonl` rotation:** `MetricsWriter._write()` rotates the file by size (10MB default, 2 backups: `metrics.jsonl.1`, `.2`) via rename under its existing write lock — no `RotatingFileHandler`, no schema change. `watchdog._load_metrics()` (and thus every consumer: `generate_status.py`, `watchdog_notify.py`, the web UI's metrics explorer) walks `metrics.jsonl` + backups newest-first until its lookback cutoff. `generate_status.py` loads events once and passes them into `run_checks(events=...)` rather than re-parsing the file a second time.

## Conversation Architecture (converse mode)

```
wake word detected
    → audio.open_session()         — opens output stream (44100Hz)
    → play greeting clip
    → loop:
        STT (faster-whisper)       — records until 1.5s silence, max 15s
        intent.classify(text)
        response priority chain:
            1. real_clip           — original Bender WAV from speech/wav/
            2. pre_gen_tts         — pre-built TTS from speech/responses/
            3. promoted_tts        — promoted AI response as static WAV
            4. handler             — weather/news/HA control
            5. ai_fallback         — Claude API → TTS
        audio.play(wav)
        conversation_log.log_turn()
        if DISMISSAL or 8s silence: break
    → audio.close_session()        — closes output stream (frees device for mic)
```

## Auto-Deploy

Changes pushed to `main` are pulled automatically by a systemd timer on BenderPi, via `scripts/git_pull.sh`.

```bash
# Check auto-pull status
sudo systemctl status bender-git-pull.timer
sudo journalctl -u bender-git-pull.service -n 20

# Manual pull
cd /home/pi/bender && git pull origin main
```

The timer polls every 5 minutes. On every new commit, `git_pull.sh` runs a guarded pipeline before it's considered deployed:

1. `py_compile` every changed `.py` file (syntax preflight).
2. `pip install -r requirements.txt`, but only if `requirements.txt` changed in the pull.
3. `sudo systemctl restart bender-converse` — blocking, bounded by a `timeout` (the service is `Type=notify` and only sends `READY=1` once the wake loop is actually listening, so a successful blocking restart *is* the health check).
4. A short post-restart `systemctl is-active --quiet` check, to catch a crash immediately after `READY=1`.

Any gate failing rolls the repo back to the previous commit (`git reset --hard`), restarts the service on the old commit, and writes `.git_pull_bad_sha` (gitignored, lives in `/home/pi/bender`, untouched by `reset --hard`) so the timer doesn't re-deploy the same broken commit every 5 minutes — it auto-clears once `origin/main` moves past that SHA. Failures are logged as loud `DEPLOY FAILED: ...` lines, grep-able via `journalctl -u bender-git-pull.service`. Test the gates without touching the real device: `bash scripts/test_git_pull.sh` (throwaway git remote + stubbed `sudo`/`systemctl`).

**Unit files are not part of auto-deploy** — see the systemd note above; `systemd/*.service` changes need a manual `cp` + `daemon-reload` on the Pi.

**journald on the Pi:** Raspberry Pi OS ships
`/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf` (`Storage=volatile`),
so the journal lived in RAM and every 22:00 shutdown erased it — `DEPLOY FAILED`
lines, tracebacks and HailoRT errors were gone by the next morning. The device now
has `/etc/systemd/journald.conf.d/50-persistent.conf` (`Storage=persistent`,
`SystemMaxUse=200M`). The drop-in **must sort after `40-`** or the vendor file wins.
Not part of auto-deploy; re-apply on a fresh Pi.

**udev rules on the Pi** (also not auto-deployed; the repo copies are in `udev/`):
`99-respeaker-xvf3800-no-autosuspend.rules` (applied 2026-07-16) and
`99-respeaker-xvf3800-control.rules` (applied 2026-09-08 — gives group `plugdev`
write access to the array so `scripts/xvf3800.py` can send `REBOOT`). Apply with
`sudo cp udev/*.rules /etc/udev/rules.d/ && sudo udevadm control --reload-rules &&
sudo udevadm trigger --attr-match=idVendor=2886 --attr-match=idProduct=001a`.

### Features
- **Puppet mode** — type text for Bender to speak, soundboard with favourites, volume control.
  A **Puppet Mode switch** sits at the top of the page. ON stops `bender-converse`
  (`POST /api/actions/toggle-mode`), so there is no wake word, no open mic and no
  sessions: a puppeteer speaking AS Bender cannot have Bender answering the room
  over the top. Entering ends any live session FIRST (writing `cfg.abort_file` and
  `cfg.end_session_file`, the same two notes the sidebar END button writes), then
  stops the service, then clears the IPC notes — nothing is left to read them, and
  `GET /api/actions/session-status` reads `cfg.session_file` directly, so a leftover
  would report a live conversation on a box where nothing is listening. Leaving
  clears the notes **before** the start, or a stale end-session note ends the first
  real conversation on turn one. Leaving costs ~23s before the wake word is live
  again (Whisper + Qwen reload). The switch has no flag of its own: it reads
  `GET /api/actions/service-status`, because a second copy of that state can drift.
  Opening the page also ends any live session on its own, before you touch anything.
  Puppet **playback** still does NOT use this route — it hands the running process a
  say-request over IPC (`say_request.py`) precisely to avoid that reload
- **Dashboard** — health, performance metrics, usage stats, watchdog alerts
- **Logs** — conversation browser, system log viewer, metrics explorer, downloads
- **Config** — edit bender_config.json and watchdog_config.json, LED colour/brightness, speech rate. **There is no Vision section.** It was deleted 2026-10-15 because every control in it was inert: Passive Mode called `/api/vision/passive`, three routes `bfbd831` deleted on 2026-04-02 along with the watcher thread behind them, and Confidence Threshold and Detection Allowlist were YOLO settings that nothing has read since `0d0d4ff` replaced YOLO with the Qwen2-VL VLM. The page polled the dead GET every 60 seconds: **93** 404s in the device journal by the day it was found. `tests/test_frontend_routes_exist.py` now checks every `/api/` call in `web/src/lib/api.js` against the app's own OpenAPI document, so the next deleted route fails the suite instead of shipping
- **Halloween mode** — a Normal/Halloween switch at the top of the Config page. It sets `halloween_mode` **and** `presence_sensor_enabled` together, because an open mic with no distance gate starts 88.6 sessions/hour from ordinary room speech and the gate fails open, so coupling them cannot cause silence. Clearing the gate checkbox decouples them and shows what that costs. In Halloween mode the AI Backend, Home Assistant and LED sections are hidden: none of them apply at the door. General, Maintenance and Watchdog stay. The gate's own controls (gate distance, release distance, confirming reads) and the session limits appear only when they are in use. **Neither flag takes effect until `bender-converse` restarts**, so the save shows the usual `restart_required` banner. The Halloween section also carries its own
**Save & Restart Bender** button, shown whenever `halloween_mode` or
`presence_sensor_enabled` differ from the saved copy. Save-then-restart as two
separate steps is how the mode got flipped in the UI and left inert on the device:
`cfg` is read once at process start, so a saved flag with no restart changes
nothing at all. The button does both and reports which mode is now live. It
compares against `savedConfig`, not a local touched-flag, so a switch flipped and
flipped back is not pending. The `presence_*` keys are now modelled in `config_schema.py` rather than passing through on `extra="allow"`, and `presence_clear_mm` must exceed `presence_max_mm` or the save is refused with 422 — equal values would flap the mic open and shut on a child standing at the boundary
- **Actions** — restart service, refresh briefings, rebuild responses, puppet-only mode toggle

### Config PUT validation

`PUT /api/config` and `PUT /api/config/watchdog` validate the incoming body against
pydantic schemas in `scripts/web/routes/config_schema.py` before writing the JSON files.
The Svelte editor PUTs the *whole* config blob on save, so the schema is intentionally
lenient about unknown keys (`extra="allow"` — `vision_*`, UI-only hex colour fields, etc.
pass through) but strict about the keys it does model: type + range checks (`oww_threshold`
0–1, positive timeouts/TTLs), `oww_model_path` must be a `.onnx`/`.tflite` under `models/`,
and `ha_url`/`local_llm_url` must be LAN/localhost http(s). Secrets (`ha_token`,
`anthropic_api_key`) are silently stripped (they belong in `.env`); path-injection keys
(`piper_bin`, `model_path`, IPC paths) are rejected with 422. `GET /api/config/schema`
returns the JSON Schema. Violations return 422 with per-field detail, surfaced by the
Config editor. `config.py` has a matching defensive type guard (`_override_type_ok`) so a
hand-edited bad `bender_config.json` skips the offending key instead of crashing at boot.

**Lenient about unknown keys cuts both ways: it lets a real key through, and it hides a
dead one.** `vision_model`, `vision_confidence_threshold`, `vision_allowlist`, `vlm_timeout`
and `vlm_lazy_poll_s` are orphans — they pass validation, they get written to
`bender_config.json`, and no code reads any of them back. The first three were YOLO settings,
dead since `0d0d4ff` replaced YOLO with the Qwen2-VL VLM; the Config page kept offering two of
them as controls until 2026-10-15. The keys are left in the file so a hand edit is not lost.

**Every one of those 422s was a 500 until 2026-10-14.** A pydantic validator that raises
`ValueError` leaves the exception OBJECT in each error's `ctx`, `e.errors(include_url=False)`
keeps it, and Starlette cannot JSON-encode the `HTTPException` detail:
`TypeError: Object of type ValueError is not JSON serializable`. So the editor showed
"500 Internal Server Error" with no field named, for `oww_threshold`, `ha_url`,
`oww_model_path`, the path-injection keys and the presence bounds alike. The save was still
refused, so nothing was corrupted — only the diagnosis was lost. It survived because
`test_config_schema.py` exercises the **model**, never the HTTP layer, and pydantic's own
*type* errors carry no `ctx`, so a bad type returned a correct 422 and only a bad *value*
broke. `_field_errors()` in `routes/config.py` now passes `include_context=False` and drops
`input`: a whole-model validator's `input` is the ENTIRE submitted body, so a save carrying
`ha_token` got it echoed back in the error body. `tests/test_web_config.py` covers both
through the route.

Both PUT responses include `restart_required` (`true` for `/api/config`, `false` for
`/api/config/watchdog`) — `cfg` (`scripts/config.py`) is an import-time singleton read once
when `bender-converse` starts, so a `bender_config.json` write is inert for the running
process until it restarts; `watchdog_config.json` is re-read from disk on every
`generate_status.py` run, so it needs no restart. The Svelte Config page (`Config.svelte`)
shows a dismissable banner with a "Restart Now" button when `restart_required` comes back true.

### WM8960 access serialization

Puppet playback, vision auto-narrate, and the ambient mic websocket each independently
stop/restart `bender-converse` to grab the single-rate WM8960 (see Critical audio
constraint above) — running two concurrently used to race (a second stop/restart could
stomp a still-playing first clip). `scripts/web/service_guard.py` centralises the
stop → work → restart sequence behind one process-wide lock; a contending request gets
`409 ServiceBusy` instead of racing. The camera MJPEG stream and mic websocket are also
capped (previously unbounded) so a backgrounded browser tab that stops reading without
closing the connection can't pin the capture device forever. Mutating web routes get
audit logging.

## Known Issues / Quirks

- **Vision told the truth about nothing (fixed 2026-10-15)** — `vlm.describe_scene` returned `""` for a failed look AND for an empty answer, and `vision.analyse_scene` flattened both into the same empty `SceneDescription`. Two callers then read "no description" as "no people". `POST /api/vision/analyse` prompted the AI with *"Your camera just scanned the room and detected nobody"*, and `VisionHandler` spoke *"I don't see anyone. Either the room's empty, or you've finally achieved irrelevance."* On this device that was the **only reachable answer**: the on-chip KV-Cache is a singleton, the resident conversation LLM holds it, and the VLM load therefore fails every time (measured 2026-07-30, `Failed to acquire KV-Cache. KV-Cache is already in use by another model.`). The route also ignored `vlm_enabled`, which only `wake_converse.py` read, and `_speak_in_background` takes `service_lease()` — so one click on **Ask Bender** cost about 23s of deafness to hear Bender confidently describe a room nothing had looked at. `describe_scene` now returns `None` for a failed look and `str` for an answer; `SceneDescription.failed()` is separate from `is_empty()` and **every caller must check it first**; the route returns 503 when `vlm_enabled` is false and 502 when there is no description; `GET /api/puppet/camera/status` reports `vision_enabled` so the Puppet page hides the button; `VisionHandler` says the eyes do not work. The empty-room lines are a claim about the room and may only be spoken after a real look. Halloween mode already drops `VisionHandler` from the chain, so the door was never exposed to this
- **webrtcvad** — use `webrtcvad-wheels` (not `webrtcvad`) — the original package's `pkg_resources` import fails on Python 3.13
- **lgpio / neopixel** — must use `--system-site-packages` venv; not pip-installable
- **scipy** — only in venv; always run prebuild via `venv/bin/python`
- **WM8960 sample rate conflict** — output (44100Hz) and mic input (16000Hz) cannot be open simultaneously on `hw:2,0`
- **Piper output is 22050Hz** — must be resampled before playback; `tts_generate.py` handles this
- **BBC Nottingham RSS** — `feeds.bbci.co.uk/news/england/nottinghamshire/rss.xml` returns 404; use UK + England feeds instead
- **BBC RSS CDATA** — `xml.etree.ElementTree` can't parse BBC's CDATA titles; use regex extraction
- **reSpeaker XVF3800 cold-boot corruption (2026-09-08)** — when the Pi cold boots with the array already plugged in (every 07:00 boot), the capture stream can come up corrupt: one `xhci-hcd: WARN: buffer overrun event for slot 1 ep 2` per USB packet, and PCM that is 91.7% exact zeros in a fixed 48-sample pattern (4 real samples, 44 zeros). Peak RMS and stddev still look alive because 1 sample in 12 is real, so the dead-feed sentinel slept through it and the wake model scored 0.001 on everything all morning. A service restart, a USB unbind/rebind and a sysfs port `disable`/enable all left it corrupt (Pi 5 cannot cut VBUS per port — all four ports are ganged, and the root disk is on USB). **Two things clear it:** replugging the cable, and the array's own `REBOOT` command over its vendor control interface (`scripts/xvf3800.py`, the protocol from respeaker's `xvf_host.py`; Seeed support's fix for the same fault after warm reboots). Verified on-device: off the bus at 0.25s, back and clean at 1.0s. **Now automatic:** `audio.mic_selftest()` measures the exact-zero fraction (`mic_zero_frac_max`, 0.5; a quiet room reads <1%), `wake_converse` sends `REBOOT` and re-measures at startup (`_recover_corrupt_mic`, metrics `mic_stream_corrupt` → `mic_stream_recovered` / `mic_stream_corrupt_persisting`), the wake loop has a matching runtime sentinel (`wake_corrupt_alarm_s`, 30s → `wake_mic_corrupt` → REBOOT → stall escalation), and `watchdog.py` raises an HA card (`mic_stream_corrupt`: warning if recovered, **error "unplug and replug"** if persisting). Needs `pyusb` (requirements) and `udev/99-respeaker-xvf3800-control.rules` on the Pi (applied 2026-09-08; not auto-deployed). Diagnose by hand with `scripts/wake_score.py --synthetic` (model OK ⇒ ~0.97) then `--record 20` (0.001 scores with audible levels ⇒ corrupt feed), or `arecord -D mic_shared` + zero%. **Proven on the cold-boot case 2026-09-09:** the array came up corrupt again at the 07:00 boot (91.9% zeros), the self-test caught it at 07:00:33, `REBOOT` re-enumerated the array in 1.38s, the second self-test read 2.6% zeros, and the wake loop was listening on a clean feed at 07:01:00 — 3.5s of automatic recovery, no human involved. So the firmware fault is a **daily** risk, not a one-off, and the recovery handles it. Verify any morning with `grep -i corrupt logs/bender.log` or the `mic_stream_corrupt` → `mic_stream_recovered` metric pair
- **openWakeWord model** — committed default is `models/hey_bender_v0.1.onnx` (the trained "hey bender" model), gitignored like all `models/*`. Fresh clone / fresh Pi: run `bash scripts/deploy_hey_bender.sh` to download it from `Schmalvis/hey-bender-oww` on HF Hub. The wake loop fails loudly (logs an error and exits non-zero) at startup if the configured `oww_model_path` file is missing — it will never silently fall back to a bundled openWakeWord model. Training/retraining: `scripts/train_hey_bender.py` (see `docs/superpowers/plans/2026-06-12-hey-bender-wake-word.md`). **v0.2 real-voice retrain (in progress, 2026-09):** capture with `scripts/capture_wake_samples.py` (130 positives / 150 hard negatives / 20 min ambient / 9.3 min conversation on the device, gitignored), freeze the split once with `scripts/split_wake_samples.py`, upload them to a **private** HF dataset with `scripts/upload_wake_samples.py`, train on Hugging Face Jobs with `hf jobs uv run --flavor t4-small --secrets HF_TOKEN scripts/train_hey_bender_hf.py -- --use-real-samples --real-positive-fraction 0.20` (the Modal script `train_hey_bender.py` still works but is superseded — HF has the model repo, the data and the credit), judge with `scripts/eval_wake_model.py` against held-out clips only, deploy with `bash scripts/deploy_hey_bender.sh <model>.onnx --threshold 0.35` (refuses to switch if the ship gates fail; `--force` overrides, `--no-eval` skips).
